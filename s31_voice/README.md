# S31 Voice — 用 ESP32-S31-Function-CoreBoard-1 语音控制宜家 MYRKISEL 灯泡

## 0. 事实核查（2026-09，实测得出，不是猜的）

| 项 | 结论 | 怎么得到的 |
|---|---|---|
| 板子芯片 | **ESP32-S31**（双核 RISC-V @320MHz，Wi-Fi 6 / BT5.4 / 802.15.4 / 千兆以太网） | `esptool --port /dev/cu.usbserial-1120 chip-id` |
| 板子 MAC | `30:ed:a0:f3:d3:b4` | 同上 |
| 工具链 | **ESP-IDF v6.1**（2026-08-27 发布）起支持 esp32s31（preview） | esp-idf releases |
| ESPHome | **不支持** esp32s31（variant 列表只到 s3/p4/c61） | 容器内 `esp32/const.py` |
| esp-sr | **支持** ESP32-S31（2.4.4 起）。实测 2.5.3 可用：`wn9_nihaoxiaozhi_tts` + `mn7_cn` | 上板跑通，见 4.1.3 |
| MYRKISEL E27 1055lm | **Wi-Fi 米家设备**，不是蓝牙 Mesh；无需网关 | 局域网 UDP:54321 miIO 握手探测到两台小米 Wi-Fi 设备 |
| 灯泡所在网段 | `192.168.0.x`，且 **IP 会漂**（实测一小时内 `.106` → `.105`） | miIO 广播扫描 + ARP |
| 板子所在网段 | `192.168.1.x` —— 和 Mac 的**无线口**不同网段，所以服务端地址必须靠发现 | 板子 DHCP 拿到 `192.168.1.7` |

> 关键推论：灯泡是 Wi-Fi 的，所以**不需要**任何蓝牙 Mesh 网关，也能做**纯局域网**控制（miIO/MIoT-LAN，拿到 token 即可），云只用于一次性取 token。

## 1. 架构

```
┌─ ESP32-S31 CoreBoard ───────────────────┐
│  驻极体麦 → ES8311 ADC → I2S 左声道       │
│              DAC 回环 ← I2S 右声道       │  ← 没喇叭也能验播放，见 4.1.7
│  AFE(VADNet/AGC) → WakeNet「你好小智」    │  ← 全离线，断网可用
│  → MultiNet mn7_cn 中文命令词            │
│  认不出来 → POST /utterance 整段 PCM     │
│  ← POST /tts 边收边播 → NS4150B → 喇叭   │  ← 需 S31_HAS_SPEAKER
└────────────────┬────────────────────────┘
                 │ Wi-Fi 6（开机 UDP 广播找服务端，不写死 IP）
                 │ 除 /health 外都带 Bearer 令牌
┌────────────────▼────────────────────────┐
│ Mac (M1 Pro, 原生跑，不走 Docker)        │
│  GET  /commands[/version] 词表 + 版本 ┐  │  ← 板子 60s 轮询，变了才拉
│  POST /command   中文句子 → 意图   │      │
│  POST /utterance 整段音频 → 意图   │      │
│  POST /tts       回话 → 16k PCM    │      │
│  STT SenseVoice-Small / TTS Kokoro│      │
│  每个响应带 ms 分段耗时             │      │
└────────────────┬───────────────────┘     │
                 │ miIO 局域网 UDP:54321    │
          ┌──────▼──────┐                  │
          │  MYRKISEL   │  ~350ms 是它的下限 │
          └─────────────┘                  │
                                           │
  Home Assistant (docker) ─────────────────┘
  只用来一次性取 did/token，控灯路径上没有它
```

控灯**不经过 HA、也不经过小米云**：M0 实测走 HA 是 0.7–1.3s，miIO 直连是 0.29–0.4s。
HA 的作用只剩下当初通过 `xiaomi_home` 集成 + 小米账号 OAuth 把 did/token 落到本地存储里。

为什么 STT/TTS 跑在本机而不是 Docker：**Docker Desktop on macOS 拿不到 GPU/ANE**，模型只能跑 CPU，延迟差几倍。

## 2. 板载引脚（从官方原理图 v1.0 / 2026-05-13 解出）

| 功能 | 网络名 | GPIO |
|---|---|---|
| ES8311 I2C SCL | `ESP_I2C_SCL` | **50** |
| ES8311 I2C SDA | `ESP_I2C_SDA` | **51** |
| I2S MCLK | `I2S_MCLK` | **52** |
| I2S BCLK | `I2S_SCLK` | **53** |
| I2S ASDOUT（codec ADC → ESP，麦克风） | `I2S_ASDOUT` | **54** |
| I2S LRCK（WS） | `I2S_LRCK` | **55** |
| I2S DSDIN（ESP → codec DAC，喇叭） | `I2S_DSDIN` | **56** |
| NS4150B 功放使能 | `PA_CTRL` | **57** |
| UART0 TX / RX | `U0TXD` / `U0RXD` | 58 / 59 |
| WS2812 RGB LED | `RGB_CTRL` | **60** |
| BOOT 键 | `BOOT` | **61** |

- 麦克风：J6 驻极体麦 → ES8311 `MIC1P/MIC1N`，**单声道模拟麦**（不是数字麦阵列，没有波束形成可用）。
- 功放：NS4150B，最大可驱动 4Ω/3W 喇叭。
- ES8311 I2C 地址：`0x18`（CE 下拉）/ `0x19`，上电用 I2C 扫描确认。
- GPIO50–57 **没有引到 J2 排针**，说明是音频专用，与文档一致。

## 4.1 M2 实测数据

麦克风增益扫描（安静房间底噪，ES8311 PGA）：

| 增益 | RMS | 峰值 |
|---|---|---|
| 0 dB | 2.0 | 6 |
| 6 dB | 4.9 | 17 |
| 12 dB | 7.6 | 23 |
| 18 dB | 14.1 | 36 |
| 24 dB | 35.0 | 129 |
| 30 dB | 69.9 | 376 |

干净的单调曲线，说明模拟链路正常。选 **24 dB**：底噪峰值 ~130，距满量程 32767 还有约 48 dB 余量，
正常说话不会削顶。

> 踩过的坑：codec 刚 `esp_codec_dev_open()` 之后**第一个读到的缓冲区是瞬态垃圾**
> （实测 RMS=4652、峰值顶满 32767），会被误判成"增益过大削顶"。所有电平测量都要先丢弃首帧。

## 4.1.1 M1 实测数据

`server/selftest.py` 闭环自测（TTS 合成 -> 喂回 STT -> 解析意图），M1 Pro CPU：

| 环节 | 冷启动 | 稳态单次 |
|---|---|---|
| Kokoro TTS | 8.0 s（含加载） | 0.31–0.51 s |
| SenseVoice STT | 5.9 s（含加载） | 0.61–0.70 s |

4/4 条指令正确落到意图上。

> 关键发现：第一版规则只有 2/4，两条失败**全是同音字**（"台灯"→"台等"、"暖光"→"暖逛"）。
> 中文短指令的识别错误绝大多数是同音而不是听错音节，所以意图解析必须有**拼音层兜底**：
> 字面规则没命中就转成无声调拼音再匹配一次。加上这层之后 4/4。
> 数字/百分比刻意**不**放进拼音层 —— 拼音里数字歧义太大，宁可漏识别也不要误触发调光。

## 4.1.2 M0 实测数据

灯泡：`light.devcea_cn_699328633_ls2303_s_2_light`（宜家麦希瑟E27 1055lm），
MIoT model `devcea.light.ls2303`，`connect_type=0`（Wi-Fi），色温 2700–6500K。

两条控制路径的延迟对比：

| 路径 | 首次 | 稳态 |
|---|---|---|
| HA → 小米云 → 灯泡 | 6.1 s | 0.7–1.3 s |
| **miIO 局域网直连** | 0.14 s（含发现） | **0.29–0.4 s** |

miIO 延迟与写入属性个数**无关**（1 个属性 415ms，3 个属性 408ms），且数值量化在
~100ms 的倍数上（196/311/415/512）—— 这是 Wi-Fi 省电模式 DTIM beacon 周期的特征，
灯泡在 beacon 之间休眠。所以 ~350ms 是这只灯的物理下限，优化空间不在单次往返，
而在**把多个属性合并成一次 `set_properties`**（"开灯+设亮度+设色温"从 3 次往返压成 1 次）。

MIoT spec（siid=2）：`piid=1` 开关(bool) / `piid=2` 亮度(int) / `piid=3` 色温(int)。

> 踩过的坑：
> - **不能写死灯泡 IP**。实测它在一小时内从 `192.168.0.106` 漂到了 `192.168.0.105`（DHCP 续租）。
>   要按 `did` 广播发现。
> - **受限广播 `255.255.255.255` 收不到回应**，必须发**定向广播** `192.168.0.255`。
>   而且这台机器同时接了两个网段，只发默认路由那张网卡也不行 —— 得枚举每张网卡的广播地址。
> - UDP 广播**会偶发丢包**，发现逻辑必须重发（实测第一次失败、第二次 60ms 成功）。
> - 官方集成的本地控制走 MIoT-Central over MQTT/TLS，**需要小米网关设备**；没网关就只能走云。
>   我们的 miIO 直控是另一套协议，不需要网关。

## 4.1.3 M3 实测数据

板上两级离线识别：`wn9_nihaoxiaozhi_tts`（唤醒词「你好小智」）+ `mn7_cn`（中文命令词）。
AFE 流水线 `[input] -> VAD(vadnet1_medium) -> WakeNet -> AGC(WakeNet) -> [output]`，
帧长 512 采样 = 32ms。

| 项 | 数值 |
|---|---|
| 最终声学回归 | 唤醒 **9/9**，命令词 **9/9** |
| 识别到灯泡响应 | 434–886 ms，中位 **492 ms**（其中 ~350ms 是灯泡自己的下限） |
| 应用镜像 | 3.44 MB / 4 MB 分区 |
| 模型镜像 | 3.43 MB / 4 MB 分区 |

回归方法：`tools/speak.sh` 用 Kokoro 合成语音、从**物理扬声器**放给板子听，
`tools/mn_regress.sh` 逐条核对板子识别出来的是不是同一条。
一条一抓而不是一轮抓到底 —— 整轮抓的话谁对谁错要靠时间戳猜，
而「听成隔壁那条」恰恰是最需要抓出来的情况。

### 词表是测出来的，不是设计出来的

**mn7_cn 有一类完全静默的失败**：命令词注册成功、出现在 active 列表、发音也对
（TTS 念的和注册的拼音逐音节比对过），就是永远不触发。实测被这样毙掉的：

| 被拒的词 | 战绩 |
|---|---|
| 含「最」的一整族（最亮/最暗/亮度最大/亮度最小/最亮模式/最暗模式/开到最亮） | 0/9 |
| 微光模式 | 0/2 |
| 冷白模式 | 0/2 |
| 把灯打开 / 把灯关掉 | 各 0/2 |
| 对照：全亮模式 | **2/2** |

不是环境、不是音量、不是注音，也没找到能预测的规律。结论很朴素：
**新词一律先跑 `tools/mn_regress.sh` 念给板子听，别信推理。**

另外三条站得住的规律：

- **每条至少 3 个音节。** 第一版留了「暖光」「最暗」这种两音节词，唤醒 4/4 但命令词
  只中 2/4，漏的正好都是两音节的；加长后同一批升到 8/12。中到的「冷光」置信度只有
  0.17，四音节的「关灯」有 0.61。
- **躲开多音字。** 「调到最亮」被 pypinyin 注音成 `diao dao zui liang`，人和 TTS 念的
  都是 `tiao ...`。注册不报错，只是永远匹配不上 —— 又一个静默失败。
- **别让两条词只差一个音节。** 「暖光模式/冷光模式」后三个音节相同，两轮里有一轮把暖光
  听成冷光（冷暖弄反是用户一眼看得见的错）。换成「黄光模式/冷光模式」后 6 次 0 混淆。

后三条是 2026-09-12 跑完 `tools/mn_regress.sh` 才转正的。**12 条不是"暂时只想到这些"，
是实测出来的上限附近** —— 往上加词会让已经好用的词一起变差，见 4.1.18。

没有单独的「最暗」命令：能表达它的说法在板上一条都不触发，而「夜灯模式」本来就是
5% + 2700K，需求已经被覆盖，「暗一点」还能连着说。

### 命令词表放在服务端

板子开机 `GET /commands` 拉词表，注册进 MultiNet。改一句命令词**不用重烧固件**。
拉不到（服务端没开/断网）就用编译进固件的那份副本 —— 离线可用不能丢。

代价是两份表会漂：固件那份只在断网时生效，平时测不出来，这轮真漂过一次。
所以 `selftest.py` 会比对两份表，`tools/sync_fallback.py` 负责按服务端那份重新生成固件那份。

### 不写死任何 IP

板子开机 UDP 广播 `S31VOICE?` 到 8791，服务端回自己的地址。

这不是过度设计：灯泡的 IP 实测一小时内从 `.106` 漂到 `.105`；而板子连上 Wi-Fi 拿到的是
`192.168.1.7`，Mac 的**无线口**却在 `192.168.0.104` —— 要是把服务端地址写死成无线口那个，
板子根本连不上。发现服务用一个不发包的 `connect()` 让内核按路由表挑「面向这块板子的
那个本机地址」，自动回了有线口的 `192.168.1.5`。

> 踩过的坑：
> - **第一次声学测试板子毫无反应，问题在 macOS 这一端**：默认输出设备被 ToDesk 的虚拟
>   声卡占着，`afplay` 的声音全进了虚拟环回，房间里一点动静都没有。得用 ffmpeg 点名
>   内置扬声器（`-f audiotoolbox -audio_device_index N`）。
>   排查顺序值得记：先加了一条每两秒打一次麦克风电平的日志，才能把「没听见」和
>   「听见了但不认」分开 —— 否则这两种完全不同的故障在日志上长得一模一样。
> - ESP-IDF v6 里内置的 `json` 组件没了，cJSON 挪到了注册表上的 `espressif/cjson`。
> - 给 `main` 显式写 `REQUIRES` 会**关掉**「默认依赖构建里全部组件」的行为，
>   连 `esp_timer`、`driver` 都得自己列。干脆别写。
> - `partitions.csv` 里那个分区必须叫 `model` —— 名字是 esp-sr 的 CMakeLists 写死的。

## 4.1.4 M4 实测数据（兜底 + TTS）

### 两条路的分工

板上 MultiNet 只认 9 条命令词。**认不出来的那句话不能丢** —— 那正好是 M3 里
被 mn7_cn 静默拒掉的一整族（最亮 / 最暗 / 把灯关掉 / 百分之三十…），而服务端的
规则引擎本来就认识它们。所以 M4 补的不是"新功能"，是**把 M3 丢掉的能力捡回来**。

    唤醒 ─┬─ MultiNet 认识 ──→ POST /command  ──→ 灯动   312–442 ms
          └─ 认不出 ────────→ POST /utterance ──→ 灯动   ~1.7 s
                             └→ POST /tts     ──→ 念回话

关键实现点：**录音必须在"知道认不认得出"之前就开始**。等 MultiNet 超时再录，
那句话早说完了。所以唤醒后一律边喂 MultiNet 边录，认出来就把录音丢掉 ——
快路径一分钱额外开销都不花。

刻意不用 WebSocket（原计划是 WS `/voice` 一次往返打包所有事）：灯该动的时刻和
回话该响的时刻是两件事，Kokoro 合成要几百毫秒，塞进同一次往返等于让灯陪 TTS 一起等。
拆成两次 HTTP，第一次回来灯就动了，第二次边收边播。少一个组件，延迟还更好。

### 端点检测：别让唤醒词的尾巴把状态机点着

第一版直接拿 `vad_state == VAD_SPEECH` 当"用户开口了"，结果每次都只录到 1.70s
就判"说完了"，服务端只听到一个「我」。原因在日志里算得出来：

    唤醒 81763 → 交出 83467 = 1704ms
    vadnet1_medium 的参数是 min noise: 992ms

唤醒词说完后 VAD 要攒够 992ms 噪声才翻成静音，我的 600ms 计数接上正好 1600ms，
而用户这时才刚开口。**唤醒词自己的尾音就在 AFE 的输出里**，状态机从一开始就被点着了。

改成认**静音→说话的跳变**：先等 VAD 落到 SILENCE（唤醒词的尾巴过去了），
再把 SPEECH 当成开口。超时那一路要特判 —— 如果 VAD 从唤醒到超时一次都没落到静音，
说明有人一直在说话，这段录音有内容，不能扔。

| 参数 | 值 | 为什么 |
|---|---|---|
| 判"说完"的静音确认 | 400 ms | vadnet 自己已有 ~992ms 迟滞，再叠长窗口纯属白加延迟 |
| 掐头的预留 | 500 ms | 服务端存下来的音频头部余量曾经是 **0.00s** —— 300ms 正好被 VAD 的检测延迟吃光 |
| 录音上限 | 6 s | 192KB，放 PSRAM |

排查手段：服务端 `SAVE_UTTERANCES=<目录>` 会把板子传上来的原始音频存成 wav。
板上端点切得对不对，只有听到它到底送了什么才说得清。

### 实测

| 用例 | 板上 | 服务端听成 | 结果 |
|---|---|---|---|

## 4.1.5 TTS：跑错权重花了大半天

**症状**：合成出来的中文声调乱七八糟。「把」念成「八」，「灯开了」听着像「登台了」，
「打开台灯」变成「大开台等」。一度以为是 SenseVoice 听错了 —— 不是，是 TTS 念错了，
STT 转得没毛病。

**这件事污染了整套测试方法**：所有声学回归都是拿 Kokoro 合成语音放给板子听的。
（好在对 M3 的结论无害：mn7_cn 吃的是**无声调**拼音，「大开台等」去掉声调仍是
`da kai tai deng`。反过来说 M3 那些数字是在声调全错的语音上打出来的，只算下限。）

**查法**：把 g2p 送进声学模型的音素串打出来，和音频对质。

    v1.0    把灯关掉 -> 'pa↓ tə→ŋ kwa→ntjau↘'      IPA + 声调箭头
    v1.1-zh 把灯关掉 -> 'ㄅㄚ3/ㄉㄥ1/ㄍ万1ㄉ要4'      注音符号 + 声调数字

音素是**对的**（除了「调」，见下），所以不是前端的问题，是声学模型没把声调唱出来。
换八个中文音色再测，同样的音素输入分数从 5/15 到 11/15 —— 说明问题出在音色向量
和声调渲染纠缠在一起，而不是文本处理。

**根因**：跑的是 `kokoro-v1_0.pth`，而 v1.0 是英语模型。它自己的 `VOICES.md` 写着：

    ### Mandarin Chinese
    - Total Mandarin Chinese training data: H hours     ← 占位符，压根没填
    | zf_xiaobei | 🚺 | C | MM minutes | D |            ← 8 个中文音色全是 C/D，数据以「分钟」计

而 `hexgrad/Kokoro-82M-v1.1-zh`（2025-02）是 **>100 小时专业中文语料、100 位说话人**，
改用注音符号 + 声调数字表示（IPA 是为英语音系设计的，普通话声调只能当尾随箭头贴上去），
还会做三声变调（你好 → ni2 hao3）。**同一个包、同一个 misaki 前端、同为 Apache-2.0**，
只要构造 `KPipeline` 时把 `repo_id` 传对就会切到 `version='1.1'` 的 g2p 分支。

所以结论不是"Kokoro 中文不行"，是**权重选错了**。不需要换引擎。

**顺带修掉一个多音字 bug**：pypinyin 单字「调」默认读 diao4，词典里也没有「调到」，
于是「调亮了」念成「掉亮了」。这和 M3 里「调到最亮」注册成 `diao dao` 永远不触发
是**同一个根因**。补在 `server/pinyin_fix.py`：`load_phrases_dict` 给词加读音，
`jieba.add_word` 保证分词先切出这个词（否则「已调到最亮」被切成 `['已调','到','最亮']`，
「调到」根本没机会被查到）。一处补丁，TTS 前端和 MultiNet 注音同时受益。

## 4.1.6 延迟拆解：慢在哪儿，之前只能猜

之前每条路径只有一个端到端毫秒数。兜底实测在 1.2–3.9s 之间飘，
但"上传慢（Wi-Fi）/ STT 慢（模型）/ 灯泡慢（miIO）"是三种病，药完全不同。
于是两端都加了分段计时：板上 `net_timing_t`（upload / wait），
服务端每个接口回一个 `ms` 字段（recv / stt / intent / exec），板子把两边拼在一行日志里。

**快路径 537 ms 的构成**（「关闭台灯」）：

| 段 | 毫秒 | 说明 |
|---|---|---|
| 意图解析 | 1 | 正则，可忽略 |
| **控灯（miIO）** | **501** | **93%** |
| 网络 + 板上 | 28 | 板子 -> 服务端 -> 板子 |

单独量灯泡的 UDP 往返（只读属性、不改状态，15 次）：
**最快 272 / 中位 374 / P90 510 / 最慢 518 ms**。

结论很干脆：**快路径已经没有可优化的软件了，它就是那只灯泡**。
自己这端只占 36ms。想再快只有两条路 —— 换灯，或者不等灯的回执就先回板子
（那样 `ok` 就成了一句谎话，没做）。

顺带发现并修掉一件事：miIO 的握手有 60 秒有效期，过期后的第一条命令要先重握，
实测 **57–211 ms**，整个落在用户等待里。加了条后台任务每 40 秒握一次
（`LightExecutor.keep_warm`），之后所有命令的握手耗时都是 **0 ms**。

**兜底路径的构成**（板上 + 服务端拼起来的一行日志，热状态）：

```
耗时 1740 ms = 上传 155(98.6KB) + 服务端 1565[STT 1153 控灯 411] + 网络 20
耗时 1514 ms = 上传 100(86.6KB) + 服务端 1396[STT  866 控灯 530] + 网络 18
```

| 段 | 毫秒 | 说明 |
|---|---|---|
| 上传 | 77–198 | 84–126KB 的 PCM，约 0.6–1.6 MB/s |
| **SenseVoice** | **866–1646** | 2.7–4.0s 音频，约 1.7–3.9x 实时 |
| 意图解析 | 0 | |
| 控灯 | 290–530 | 又是那只灯泡 |
| 网络 | 18–20 | |

（服务端刚重启后的第一句 STT 是 6940ms —— 模型冷启动，不是常态。）
两个大头是 STT 和灯泡；上传只占 0.1–0.2s，之前担心的"Wi-Fi 传音频慢"不成立。

**这里的分段第一版是错的**，值得记一笔：板上算"其它 = 总时间 − 上传 − 服务端"，
出来是负数。原因是服务端的计时从处理函数进入就开始，而它等 body 收完的那段
（`recv`）**正是板子在上传的那段** —— 同一段墙钟时间被减了两次。
改成扣掉 `recv` 之后各项才加得起来（155+1565+20=1740）。
负数一眼就看得出来；要是它凑巧算出个合理的正数，就会被当成真数据用下去。

## 4.1.7 没有喇叭也能验播放：DAC 回环

ES8311 的驱动会写 `REG44=0x58`（"internal reference ADCL+DACR"），把 **DAC 的数据
镜像到 I2S 输入的右声道** —— 本来是给 AEC 当参考通道用的。我们把 I2S 从单声道
改成双声道收之后，左 = 麦克风、右 = 板子刚播出去的东西。

于是"板子到底有没有把音频送出去"从推断变成了实测。之前只有反证
（write 返回 OK、耗时等于音频时长、寄存器读回来是对的），现在有正证：

```
播放自检：1kHz 幅度 8654（送出去 12000，72%，音量 70），
          回环 RMS 7206，同期麦克风 RMS 21，6656 采样
```

用 Goertzel 只算 1kHz 那一个频点（每样本三次乘加），不在 feed 任务里做 FFT。
幅度打不满是对的 —— 回环点在数字音量之后，音量 70 就该看到七成。
真正的判据是**这个频率在不在**，以及同期麦克风那一路贴着底噪（RMS 21），
证明右声道不是从左边串过来的。

`CONFIG_S31_HAS_SPEAKER=n` 时每次开机自动跑一遍。它只验到数字段
（I2S TX -> DAC 数字通路 -> 音量/静音）；模拟输出、NS4150B、喇叭仍然要真喇叭才验得了。
代价是 I2S 收发带宽翻倍（16k 立体声 = 64KB/s），以及播放时要把单声道展开成双声道
（`audio_hw_write_mono`）。换来的除了这个观测点，还有以后上 AEC 时现成的参考通道。

## 4.1.8 命令词表热更新

之前改一条命令词要重烧或重启板子（重建模型 4 秒，还得够得着串口）。现在：

- 服务端 `/commands` 带一个 **版本号 = 词表内容的 sha256 前 12 位**。
  用内容哈希而不是手工序号 —— 手工序号一定会有人忘了改，
  而忘了改的后果是板子挂着旧表还以为是新的。
- 板子每 60 秒问一次 `/commands/version`（几十字节，而整表 1.2KB），
  变了才拉全表。
- 拉到的表先进**暂存区**，由 detect 任务在"没在识别命令词"的空档里换上去
  （`sr_commands_begin/commit`）。不直接改在用的那张：
  detect 任务正拿着 id 去查文本，写到一半会读出乱码。

实测（服务端注释掉一条词再恢复，板子没重启）：

I (425140) sr: 命令词表已热更新，现在 8 条

## 4.1.9 鉴权

之前同一局域网里谁都能 POST 一条命令控灯。现在除 `/health` 外所有接口
（含 WebSocket 握手）都要 `Authorization: Bearer $API_TOKEN`。

- 威胁模型是"同网段的其他设备/人"，不是拿到本机权限的攻击者 ——
  所以一个共享 bearer 就够，没上 TLS/mTLS。
- 令牌比较用 `hmac.compare_digest`，不是 `==`：逐字节的提前返回会泄露正确前缀的长度。
- `API_TOKEN` 留空 = 完全关掉鉴权，老用法照跑。
- 板子那端是 `CONFIG_S31_API_TOKEN`（写在 gitignore 的 `sdkconfig.secret` 里）。
  板上所有请求走同一个 `set_auth()`，不给"某条路径忘了加头"留缝。
- `/health` 故意不鉴权（探针，被探到不算泄密）；原来挂在它上面的详细信息
  搬到了要令牌的 `/status`。
- `tools/_auth.sh` 给脚本共用，令牌的读法只有一处。

## 4.1.10 nsnet2：占了 340KB，一次都没跑过

`CONFIG_SR_NSN_NSNET2=y` 把模型打进了 flash，但 `AFE_TYPE_SR` 下我们
`se_init=false`，降噪压根没进流水线（开机日志的 pipeline 里也确实没有它）。
换回 `CONFIG_SR_NSN_WEBRTC`（纯代码），`srmodels.bin` 从 3598400 降到 3260454 字节，
**省 330KB**。真要开降噪时把那行放开、`se_init` 改 true 即可。

## 4.1.11 唤醒词实测（`tools/wake_bench.py`）

此前唤醒词一个数都没有 —— "灵不灵"只能靠体感争。信号一律在数字域调幅/混音，
不拧系统音量（可复现，且绕开这台机器上被 ToDesk 虚拟声卡占着的默认输出）。

### 灵敏度（衰减代理）

| 档位 | 唤醒 | 板子自报麦克风峰值（中位） |
|---|---|---|
| 0 dB（基准 ≈2 m） | 6/6 | 1093 |
| −6 dB（≈4 m） | 6/6 | 644 |
| −12 dB（≈8 m） | 5/6 | 344 |
| −18 dB（≈16 m） | 4/6 | 204 |

**这是性能上界，不是等效距离**：衰减 6 dB 在自由场里等于距离翻倍，
但真实远场除了变小还会变混响，直达声/混响比下降是纯衰减模拟不出来的。
真远场要抱着板子走。

### 抗噪（混粉红噪声）

| 档位 | 唤醒 |
|---|---|
| 安静 | 6/6 |
| SNR ≈ 20 dB | 6/6 |
| SNR ≈ 10 dB | 6/6 |
| SNR ≈ 5 dB | **1/6** |
| SNR ≈ 0 dB | 0/6 |

**10 dB 和 5 dB 之间是一道悬崖**，不是缓坡。这是目前最硬的一个限制：
安静房间和有点背景音都没问题，但真吵起来（电视开着、有人聊天）基本叫不醒。
要改善只能上降噪 —— `nsnet2` 的模型还在（4.1.10 只是没打进 flash），
把 `se_init` 打开就能测，但那要先有一套嘈杂环境的回归。

### 误触发

**静默监听 30 分钟（不放任何声音，只听房间本身）：0 次误唤醒、0 次误动灯、0 次误上传。**
环境电平 RMS 中位 21。这个数只能给出「约 6 次/小时以内」的上界
（零事件的三倍法则），而且深夜安静房间是最容易过的场景。

放干扰语料的版本更有信息量。**语料按"和唤醒词的声音差多远"分三档** ——
这一步不做的话数字会骗人：

每句放 3 遍，共 12.4 分钟：

| 档 | 唤醒 | 怎么读 |
|---|---|---|
| 同音 / 仅声调不同 | 12/12 | **醒了是对的，不算误报** |
| 近音（末音节或语序不同） | 8/21 | 误唤醒，38% |
| **日常句子** | **0/36** | 误唤醒，且最要命 —— **一次都没有** |
| 真实误唤醒 | 8/57 | |
| 其中误识别成命令词 | **0** | 只有这些会真的动灯 |

这张表的结论很实用：**正常说话不会误唤醒它**（0/36），
误唤醒集中在"刻意做得很像"的那一档（38%）—— 也就是说，
现实里只有人真的说了句很像「你好小智」的话才会中招，而那本来也不算冤枉。

### 这里踩了个自己挖的坑

第一版把「你好小志」「泥好小智」「你好小知」「尼豪小治」也当成干扰词，
被叫醒就记成误唤醒，算出 **157 次/小时**，看着像个严重问题。

但「你好小志」= `nǐ hǎo xiǎo zhì`，和「你好小智」**逐字同音同调**。
唤醒词识别的是声音不是字 —— 认出它是对的，不是错的。另外三条只差声调，
而 WakeNet 对声调本来就不敏感。

是 SenseVoice 把那几条原样转写回「你好，小智。」才让我发现的：

```
'你好，小易。'  '你好，小智。'  'you好，小七。'  'you好，小度。'  'you好，小池。'
```

分类之后真实误唤醒率从 157 次/小时降到 8/57 次播放，而且日常句子那档是 **0/36**
—— **同一批录音，同一块板子，差别只在有没有把"字不同"和"音不同"分开**。

**教训**：测试语料本身也是要验证的东西。一个分类错误的语料集，
会稳定地产出一个精确而错误的数字，而且它看起来完全像真的。

## 4.1.12 一次真实故障：语音控灯整个哑掉

**现象**：说什么都不动。板子唤醒正常、灯泡在线、服务端 `/health` 返回 200，
两边日志看着都没毛病。

**根因是两层，第二层才是真正让它"无法自愈"的那个。**

**第一层（触发）**：Mac 上那张 USB 有线网卡（`en12`，持有 `192.168.1.5`）掉了。
这个工程的网络拓扑本来就别扭 —— 板子的 Wi-Fi 在 `192.168.1.x`，
Mac 的 Wi-Fi 在 `192.168.0.x`，两者**只能靠那张有线网卡**在同一网段里相遇。
网卡一掉，两台机器就没有共同网段了。

**第二层（放大成静默故障）**：发现服务用的是"不发包的 UDP connect + `getsockname`"
问内核"去板子该用哪个源地址"。这招在只有物理网卡时是对的。但有线网卡一走，
那条 `192.168.1.0/24` 的明细路由跟着消失，代理软件的 TUN 网卡
（`utun1024`，地址 `198.18.0.1`）就把这条路由接管了。内核于是诚实地回答
"用 `198.18.0.1`" —— 一个对板子毫无意义的地址。

```
22:04:50 discovery 板子 192.168.1.7 来问路，回 {"host": "198.18.0.1", "port": 8790}
```

日志里这行看着完全像成功。板子把它存下来，之后每个请求都 `ESP_ERR_HTTP_CONNECT`，
而且**到重启为止都不会再改** —— 服务端地址只在开机发现一次。

**改了三处：**

1. **服务端不再问路由表。** 只从真实网卡上列地址，明确剔掉没意义的段
   （`127/8`、`169.254/16`、`198.18/15` —— 最后这个是基准测试段，
   被各种代理 TUN 拿来当假网关），按"和板子同网段"排序。
   一个同网段的都没有时在日志里**喊出来**，而不是默默回一个能骗过所有人的地址。

2. **回的是候选列表不是单个地址**（`{"host": …, "hosts": [ … ]}`，
   `host` 留着兼容旧固件）。一台机器挂在几个网段上时，
   哪个能连上只有板子试得出来 —— 服务端本来就猜不准。
   板子拿到列表后逐个 `GET /health`（免鉴权，正是给探活用的），第一个应答的胜出。
   **别信别人给的地址，自己验一下。**

3. **板子会重新找。** 每分钟那次词表版本轮询顺手当心跳：连续 3 次够不着就重新发现；
   开机没找到也会一直找下去。另外，一条语音命令因为"连不上"而失败时，
   当场就重找一次 —— 那句已经废了，但下一句能用。
   两条任务都可能触发重找，所以加了把锁排队（都在写同一个 URL）。

**验证**（`DISCOVERY_FAKE_HOSTS=198.18.0.1` 一键重演这个故障 ——
没这个钩子，这个 bug 只能靠物理拔网线来复现）：

```
W (5246) net: 候选 198.18.0.1:8790 连不上，试下一个
W (5251) net: 1 个候选一个都连不上
W (7272) net: 没找到服务端，识别结果只会打日志      <- 以前这里是"广播找到服务端"
```

服务端恢复正常后，板子**没有重启**，60 秒后自己接上了：

```
I (68343) net: 服务端在 http://192.168.1.5:8790（2 个候选里的第 1 个）
I (68344) main: 找到服务端了，补拉一次词表
```

另一半也验了 —— 板子已经握着好地址、服务端随后消失的情况：

```
W (188955) net: /commands/version 请求失败: ESP_ERR_HTTP_CONNECT
W (248981) net: /commands/version 请求失败: ESP_ERR_HTTP_CONNECT
W (309011) main: 连续 3 次够不着 http://192.168.1.5:8790，重新找服务端
W (312023) net: 没找到服务端，识别结果只会打日志
```

前两次失败故意不喊（服务端重启一下很正常，没必要刷屏），第三次才动作。

**教训**：一个"看起来成功"的错误答案，比一个明确的失败贵得多 ——
它把排查方向从"网络"引到了"语音识别"。凡是靠系统状态推断出来的答案
（路由表、设备列表、默认设备），都该当成猜测，用一次真实往返去验证它。

## 4.1.13 M7：为什么整套东西是围着"锚定"长出来的

Tivoli 没有厂商 API（`/httpapi.asp` 404 —— 它是 Libre LS1.5 模块，不是 LinkPlay），
**Google Cast 也是死的**：`:8009` 在待机和开机两种状态下都对四个 TLS 版本一律 RST
（2026-09-11 复测，roadmap 的 R1 就此定案）。能用的只有红外和 AirPlay。

红外是开环的，而且语义比"开环"还糟：

    POWER  是 toggle —— 按之前不知道它开着还是关着
    SOURCE 是 cycle  —— 按之前不知道停在哪一档

**没有一条红外指令能告诉我们按完之后设备处在什么状态。** 而一次成功的 AirPlay 推流
同时证明三件事：设备开着、源停在 WiFi、网络通。于是：

    盲按（现状）
      POWER? ──→ SOURCE? ×n ──→ 落在 WiFi/AUX/BT/FM 的哪一个？不知道

    锚定（本方案）
      推流成功 ──→ 确知：已开机 + 在 WiFi 源 ──→ SOURCE × 3 ──→ 确定落到 FM

实测「打开收音机」= 锚定 → SOURCE×3 → 精确落到 FM，2.9 秒，一次都没偏。

### 推流不能用 pyatv —— 这条路走死了，别再走一遍

pyatv 的 RAOP 能走到握手一半：transient 配对成功、密钥都推导出来了，然后 `SETUP`
石沉大海。把 pyatv 完全绕开、手写裸 RTSP 又验一遍：`ANNOUNCE` 200、`SETUP` 403。

根因是 pyatv 在 RAOP 这条路上**从不给 RTSP 开加密**（整个包里只有 MRP 调
`enable_encryption`），而这台严格的 AirPlay 2 接收端（`/info` 里
`PTPInfo: Apple Airplay 2.0.10 SDK PTP`）配对完就要求加密通道，明文 SETUP 它不报错、
直接丢弃。这是库的能力缺口，配置绕不过去。顺带排除掉的岔路：改 `timingProtocol`
为 PTP 没用；网页上那个 AirPlay 密码对 **RTSP Digest 是对的**（`ANNOUNCE` 200）
但对 HAP/SRP 配对是错的 —— 两者不是同一个凭据，而 transient 配对用的是写死的
PIN 3939，根本不看密码。

**改用 macOS 自己的 AirPlay 栈**：系统输出指着 Tivoli，我们只管 `afplay`。
Apple 的实现当然没问题（实测不要密码、出声正常）。代价四条：

- **切走 AirPlay 会拆掉连接**，而且 CoreAudio 那层没有命令行能把它选回来
  （`SwitchAudioSource` 只能在已存在的设备之间切，断开之后这个设备干脆不在列表里）。
  所以有了 `tools/airplay_relink.sh` —— UI 脚本点控制中心。
  控制中心里设备名**没有暴露给辅助功能**（macOS 26.2 实测 AXTitle/AXDescription 全空），
  只能逐个点、点完回头问 `SwitchAudioSource` 当前输出变成了谁。
- 拿不到"歌名显示在 Tivoli 屏上" —— afplay 不送元数据。
- 系统音量就是 Tivoli 的音量，同一个旋钮。**但这反过来是白捡的**：发红外 VOL−
  之后系统音量跟着从 18 掉到 12 —— AirPlay 会把设备音量同步回 macOS，
  这是整套系统里唯一能**读回来**的设备状态。所以音量走网络绝对值（593ms）
  而不是红外（1370ms，且开环记账必然跟实体遥控器对不上）。
- 锚定从"传感器 + 执行器"降级成偏执行器：afplay 不管设备在不在都返回 0，
  拿不到推流成功的回执。现在的判据是"TCP :7000 可达 **且** macOS 链路在"，101ms。

### IR 的 POWER 是硬断电，不是待机

按下去 WiFi 一起掉（ping 立刻不通），重新入网要 **28 秒**，而且 macOS 的 AirPlay
链路断了就**不会自己回来**（等 48 秒仍然没回）。`keepAliveLowPower=true` 这个
mDNS 字段具有误导性。所以**默认不碰 POWER** —— 关机一次的代价是把音乐链路一起废掉。

好消息是失败模式可以区分，而且比设计时预想的更清晰：

    ping/ARP 就失败（Host is down，1ms）   -> 设备真关机了
    TCP :7000 通但推不动                    -> 设备开着，只是链路没挂上

## 4.1.14 M8：网易云这条链是唯一会自己坏掉的

cookie 会过期、接口会变、歌会下架、VIP 会拦。所以它被关在 `netease.py` 一个文件里，
坏了不牵连 FM 和灯。今晚踩到的三件事：

- **`/weapi/cloudsearch/get/web` 已经废了**，一律回 `{"code":50000005}`（风控）。
  老接口 `/weapi/search/get` 照常工作，只是字段名是老一套
  （`artists`/`album`/`duration` 而不是 `ar`/`al`/`dt`）。
- **搜索排名很差，必须再拉一次 `song/detail` 拿 `pop`（热度）来排。**
  搜"红豆"时它把一堆翻唱排在王菲前面；按 pop 排立刻就对了。
  多一次往返（~200ms）换的是"放的是不是用户想的那首"，值。
- **筛选顺序是歌名先于歌手。** 反过来的话，「播放周杰伦的稻香」会先筛出一堆
  周杰伦的歌、再在里面找不到《稻香》、然后退回去按热度挑 —— 结果放了《刀马旦》。
  歌名是用户说得最具体的那个词，它筛不出东西就该认输。

还有一条不是 bug 的事实：**周杰伦的原唱不在网易云上**（版权在别家），搜到的全是翻唱。
所以点了歌手却匹配不上时，回话必须说出来 ——
「网易云上没有周杰伦的《稻香》，给你放 Lucky小爱 的《稻香》」。
默默放个翻唱还说"播放周杰伦的稻香"，是在骗人。

登录靠扫码：`tools/netease_login.py`，cookie 落在 `server/.netease_cookie`（已 gitignore，权限 600）。

**更正（2026-09-13）**：本节里「按 pop 排立刻就对了」这条在更宽的样本上不成立 ——
网易云的 `pop` 会饱和在 100，同一首歌的多个版本经常并列满分。见 4.1.22。

## 4.1.15 M10：三台设备之后，多出来的是"消歧"

规则层从一个域扩到三个，最大的新问题不是规则变多，是**同一句话现在有三种意思**：

    "关掉"   -> 关灯？关音响？停音乐？
    "下一个" -> 换台？下一首？

解法是记住上一次**成功**操作的是哪台设备（`executor.Router.last_domain`）。
失败的不算 —— 一条没执行成的命令不该改变后面那句"关掉"的含义。

规则表的顺序因此多了一条硬约束：**带设备名的规则必须排在泛化词前面**。
"打开收音机"和"打开台灯"共享"打开"；顺序反了，每一句"打开收音机"都会去开灯。
这类错都是自检当场抓出来的（`python intent.py` 会把词表逐条解析一遍），
其中两条是真回归：收紧灯的开关词之后「打开台灯 / 关闭台灯」——
**板上词表的头两条** —— 直接不认了。

本地 LLM（Ollama + Qwen3-4B 4bit）是**第三层**，只在规则层和拼音层都没命中之后才问，
硬超时 1.5 秒，超时就当没有这一层。选 4B 不选 7B 是被 16GB 内存逼的。
两个用途都很窄（意图分类、氛围点歌抽关键词），而且输出**必须过白名单** ——
模型很乐意发明一个 `tivoli/set_frequency`，而下游是真会动的硬件。

板上 MultiNet 的 Tivoli 候选词放在 `_MULTINET_CANDIDATES` 里，**默认不发给板子**。
按 4.1.3 的教训，没过声学回归的词进了表，表现是"注册成功、日志正常、永远不触发"，
而板子这时已经把兜底路径让给了这条按不动的命令词。先单独验：

    tools/mn_regress.sh 打开收音机 关掉收音机 换一个台 …
    MULTINET_INCLUDE_CANDIDATES=1 ./run.sh     # 过了再放进正式表

预设位起中文名（"放音乐之声"）走 `server/fm_presets.json`，是配置不是代码。
**按频率调台（"调到 101.7"）不做** —— 读不回显示屏，盲数步数必然漂移。

## 4.1.16 M6：出声实测，以及手册和实测对不上的地方

这一节是 Tivoli 那半边的地基。原 roadmap 把 M6 列成闸门是对的 ——
真跑完之后，**原设计里有一半的假设被推翻了**。`server/tivoli.json` 里每个常数
旁边都写了它是怎么来的，`measured: true` 只有在全部量完之后才置上。

### 源循环：手册是错的

手册原文说 SOURCE 键 *"cycle between WiFi, FM, DAB (if available), Bluetooth, and Auxiliary"*。
**本机实测是 `wifi → aux → bt → fm`，一圈 4 档，没有 DAB。**
所以 wifi 到 fm 是 **3 次** SOURCE，不是手册顺序算出来的 1 次。

当初坚持"数一遍再写进配置、不照手册抄"，就是为了这个。猜错的后果不是报错，
是每次「打开收音机」都安静地落到隔壁源上，而我们连落错了都发现不了。

### 遥控器做不到"下一个电台"

查了手册才定案，不是试出来的：自动搜台是 *"Autoscan Up: To autoscan to a higher
frequency, quickly **double press the bezel**"* —— **只有机身旋钮能做**。
遥控器按键全集是 MUTE / ALARM / 方向键+SELECT / 音量± / 预设1-6 / SETTINGS /
SOURCE / SLEEP / POWER，没有搜台。

方向键在 FM 下确实能调（▲▼ 和 ◀▶ **两组都能**，上/右 +0.05MHz，下/左 −0.05MHz），
但 0.05 只是微调 —— 国内台间隔至少 0.1MHz，按一下什么台都换不到。
所以 `station_step` 老老实实说自己是微调，换台靠预设。

（手册里 `FM Tuning Steps` 是 SETTINGS 里的可调项，改成 0.1 能让方向键一按一个
频道位。这个没做 —— 要在机器上手动走菜单，而且改了也还是"挪一格"不是"搜下一个台"。）

### 长按存台：波形对了三次才对

这是全程最反直觉的一段，**三次尝试才成**：

| 做法 | 结果 |
|---|---|
| 按 108ms 周期重发整个 NEC 帧 | 设备把每一帧都当成独立短按，连着切了 7 次台（8~45 帧全试过） |
| 发 NEC 重复码，但用 `repeat` 循环发 N 次独立的 `transmit_raw` | 还是不行 |
| **一次 `transmit` 里发完首帧 + 全部重复码** | **成了** |

把真遥控器的长按录下来才定的案（`remote_receiver` + `dump: all`）：

    短按   NEC 帧(0xE01F) + 1 个重复码
    长按   NEC 帧(0xE01F) + 约 18 个重复码，持续 1.84 秒
    重复码 9125us 载波 / 2314us 空 / 526us 载波，108ms 周期

关键是**第二次的波形其实已经对了**（9000/2250/560 和实测的 9125/2314/526 差几个百分点），
错的是发法：发射器开着 `non_blocking: true`，拆成多次 `transmit_raw` 会各自排队调度，
108ms 的节拍在中间散掉 —— **而节拍正是设备用来数长按的东西**。
所以现在整串重复码在一条 lambda 里 build 成单次发射，见 `esphome/config/tivoli_ir.yaml`。

阈值实测：10 帧还是短按（切台），**18 帧起判成长按**，配置取 20 留余量。

### 长按是 toggle，不是覆盖

手册这一段自相矛盾 —— 同时说 hold 是"保存"又是"删除"。实测定案：

    10 帧 -> 切台   （没到阈值）
    18 帧 -> 删除   （位子原来是满的）
    26 帧 -> 添加   （上一步删空了）
    36 帧 -> 删除   （又满了）

**位子空则存当前台，位子满则删。** 所以「把这个台存到预设三」不能傻按一下 ——
位子有台的话按一下是把它**删了**。`TivoliExecutor` 因此维护一张
`preset_occupied` 表并落盘：满的先删一次再存，空的直接存。

这张表只有我们自己操作时才准。有人拿实体遥控器动过预设，它就开始腐化，
而腐化的后果是"说存台、结果把台删了"，**用户看不见**（屏幕我们读不到）。
这是整个 Tivoli 侧最脆的一处记账。

### 板子的喇叭：日常回话不该走 Tivoli

J9 接上喇叭之后，回话有了第二条出路。**这条比 Tivoli 那条好得多**：
不依赖音响开着、不依赖 AirPlay 链路活着、延迟也低。所以分工定成：

    日常语音回话  ->  S31 板载喇叭
    放音乐        ->  Tivoli

固件那条路代码本来就写好了，只差 `CONFIG_S31_HAS_SPEAKER=y`。
输出音量原来在 `main.c` 里写死 70，接上实测偏小听不清，改成
`CONFIG_S31_SPEAKER_VOLUME`（默认 85）—— 做成配置项是因为这个值只能放出来听，
推不出来：太大削顶失真，太小听不见。

## 4.1.17 AirPlay 这条链上，"成功"是不可信的

Tivoli 那半边接完之后，一晚上抓到三个 bug，**根子是同一个**：
`afplay` 往的是"系统当前默认输出"，而它**不管声音去了哪里都返回 0**。
整条链上没有任何一层会告诉我们声音其实没到音响 —— 服务端日志写着
「推流 王菲的《红豆》」、HTTP 接口回 `ok: true`，而歌从 MacBook 自己的喇叭里出来。

这类 bug 的共同形状是：**失败没有回执，只有沉默**。三个都是这么冒出来的。

### 一：音乐路径根本不检查链路

`MusicExecutor` 拿到文件直接 `afplay`。而链路**只要听一次收音机就会断**
（红外把源从 WiFi 切到 FM，macOS 那头的 AirPlay 就没了）—— 也就是说这不是
异常路径，是主路径。修法是播放前 `_ensure_link()`：查链路、断了自动重挂、
**挂不上就拒绝播放**，而不是退而求其次放给电脑。

### 二：`ensure_wifi` 把"链路断了"误读成"设备关着"，按了 POWER

原来的逻辑是「锚定失败 → 按 POWER 试试看」，看起来合理。但换用 macOS 的
AirPlay 栈之后，`anchor()` 失败有两个完全不同的原因：设备关着，或者链路断了。
两者混在一起的后果是：用户切去听 FM，再说一句「打开收音机」——
代码读到锚定失败、按下 POWER，**把一台开着的收音机关掉了**。

而 POWER 是 toggle，在错误前提下按它是破坏性的，事后也没有回执能发现按错了。
所以判据必须是**网络层面真的够不着**（`reachable()`），不是**推不了流**（`anchor()`）。
这一条值得记死：

    anchor() 失败  ≠  设备关着
    reachable() 失败 = 设备关着

顺带修掉一个隐藏在旁边的错：开机到重新入网实测要 **28 秒**，而原来
`power_settle_ms` 只等 3 秒就去重试，必然失败 —— 现在改成轮询等最多 40 秒。

### 三：播放中途断线，afplay 会跟着输出一起迁到电脑喇叭上

实测：一首 4 分 20 秒的歌放到 **50 秒**时 AirPlay 设备从 CoreAudio 里消失，
afplay 被打断、声音掉回 MacBook。`_ensure_link()` 只在每首歌**之前**查，
一首歌播放中途断掉它看不见。

现在有个看门狗每 4 秒回头看一眼链路，断了立刻停 afplay、挂回去、从断点续（最多两次）。
**根因还没查** —— 查它必须让机器出声，留到下次。

### 这一节的方法论

三个 bug 里有两个是在**用户报告"声音从电脑出来了"之后**才发现的，
而服务端日志当时全是绿的。教训不是"要加日志"，是：

> 一条链路如果没有回执，就不能把"命令发出去了"当成"事情做成了"。
> 要么找到一个能读回来的信号（这里是 `SwitchAudioSource -c`），要么明确承认不知道。

Tivoli 这台机器把这个教训给足了：红外全程没有回执，AirPlay 的成功回执被
换实现时丢掉了，而 `afplay` 的返回值是假的。唯一真正能读回来的东西，
是 macOS 自己认为当前输出设备是谁 —— 整套系统就吊在这一个信号上。

## 4.1.18 M15 声学回归：词表容量是零和的

`tools/mn_regress.sh` 把每条命令词合成成语音、从物理扬声器放给板子听，
一条一抓，核对板子识别出来的是不是同一条。新增命令词之前先跑它。

起因是想把 Tivoli 和空调的 14 条候选词一起加到板上。加完一测，**全表崩了**：

| 词表条数 | 命令词正确 | 置信度 |
|---|---|---|
| 9 条 | 4/5 | 0.25 ~ 0.47 |
| 13 条 | 5/7 | 0.14 ~ 0.45 |
| 23 条 | **2/7** | 0.15 ~ 0.16 |

关键不在"通过率掉了"，在于**所有词一起变差，包括原本健康的基线词**。
不是某几个新词不好 —— 候选越多，每个词越难把自己和其他候选拉开声学距离，
和 §4.1.3 里两音节词失效是同一个机制。

> 往板上加词是**零和的**：加一条，就让其余每一条都难一点。
> 所以加词只能是**替换**，不能是追加，而且每次都得重跑回归。

最终 12 条，转正的三条实测：关掉收音机 0.45（全表最稳）/ 打开收音机 0.14~0.26（3/4）/ 暂停播放 0.16。

### 「下一首」没进去，以及我换词时犯的方法错误

「下一首歌」0/3 静默失效（注册成功、日志正常、发音也对，就是永不触发，§4.1.3 那一类）。
按那一节的教训，不该反复试同一个词，该换说法 —— 于是换成「换一首歌」，**0/2，一样**。
同一轮基线「打开收音机」✓ 0.16、唤醒 3/3，所以测试台是好的。

错在换词的方式：这两条共享「一首歌」三个音，五个音节里同了三个，
**根本不是两次独立试验，等于把同一个音串试了两遍**。真要再试，得换音串不重叠的，
比如「播放下一首」或「切换歌曲」。

不过没进板上词表 ≠ 不能用：板上词表只是**唤醒后的离线快路**，
匹配不上会照常把整段音频送到服务端走 SenseVoice，意图层认得「下一首」，只是慢一秒左右。
而且容量是零和的，空出这一格让剩下的都好过一点。

### 回归本身的三个 bug —— 每一个都会让结论完全错掉

测试工具出错比被测物出错更危险，因为错的是**你用来判断对错的那把尺子**。
这三个都是先得出了一个像模像样的错误结论，才被抓出来的：

1. **压音量功能自伤，整轮 0/10。** 板子一唤醒就 POST `/wake`，服务端把系统音量从 85
   压到 12 好让麦克风听清 —— 而回归的命令词正是从**同一对喇叭**放出去的。
   于是每条命令词都在音量 12 下播出去。表现是"所有命令词全部静默失效"，
   最难查的那种故障。修法不是关掉压音量，是**只在输出指着 Tivoli 时才压**：
   板子自己的喇叭在放音时，我们根本不是噪音源。
2. **回归会真的执行命令。** 词表里有「播放我的收藏」，它执行时发现 AirPlay 链路断了
   就去重挂，**把系统音频输出从内置喇叭切到了 Tivoli**，后面每条测试词都在往
   没人听的地方放，唤醒掉到 1/7，看起来像板子坏了。加了 `DRY_RUN=1`：只识别不执行。
3. **追问窗口对着空气说话。** 每条成功命令之后窗口开着，录到 0.7 秒尾音/回声就判"说完了"
   发上去，服务端听成「没有。😮」，板子念一句「这个我还不会」——
   整个过程 6 秒，把下一轮唤醒也挡掉了。修法见 4.1.20。

还有一个不算 bug 但同样致命的：等待回归结束的后台循环写成了 `until ! pgrep -f mn_regress`，
而 `pgrep -f` 把**等待循环自己的命令行**也匹配上了 —— 三个循环互相等对方退出，
空转 85 分钟，回归一分钟都没跑。`pgrep -f` 匹配完整命令行，写等待循环时它总会匹配到自己。

### 用户的观察比日志值钱

第 1 个 bug 是这么定位的：日志显示"唤醒 0/10"，我正准备去查麦克风增益，
用户说了两句话 —— **「你只说了你好小智，没有其他音」**、**「或者真正的命令声音极小」**。
第二句直接指向了音量，而服务端日志里压音量那一行看起来完全正常（它确实成功了）。

> 开着麦克风的系统，日志里没有"房间里实际听起来怎么样"这一维。
> 而这一维经常就是答案。


## 4.1.19 M12 空调：全系统唯一一台闭环设备

录真遥控器之前的计划是"学三个红外码：电源 / 温度+ / 温度−"，
并且因为**电源是 toggle 且不宜连按**，准备照 4.1.17 的教训小心处理。

录完发现前提就是错的。它说的是 **Coolix**，而 Coolix **每一帧发的是整机状态** ——
电源、模式、风速、目标温度一起，三个字节各跟一个自己的反码
（实捕：`B2 4D` `FF 00` `D0 2F`）。

"按温度+"根本不是一条离散命令，而是**一帧温度更高的完整状态**。捕获里的铁证：
电源键和温度−键打出了**逐字节相同的帧**（`0xB2FFD0` = 26℃）——
因为温度+ 先把它推到了 27℃（`0xB2FF90`），温度− 又推了回来。

这一下把它和这套系统里其它设备彻底分开了：

| | Tivoli | 空调 |
|---|---|---|
| 命令语义 | POWER 是 toggle，SOURCE 是循环 | 每条都是**绝对状态** |
| 失步 | 会。要靠锚定重新对齐（4.1.13） | 不会。没有可失步的东西 |
| 状态 | 只能维护影子，猜 | 遥控器一发，`receiver_id` 收得到，**读得回来** |

所以它拿到的是一个真的 `climate` 实体，不是三个按钮："打开空调"设成
`mode=cool` 这个绝对状态，而不是按一个意思是"把你现在的状态取反"的键。
`receiver_id: ir_rx` 让人用实体遥控器时 Home Assistant 也跟得上，影子状态不会悄悄烂掉。

一个坑：相对温度调节（"高一点"）需要先读当前温度，而刚发完的那条命令
HA 那边的状态还没更新，读回来是旧值，连说两次"高一点"只升一度。
`aircon.py` 里用 `_last_set` 缓存自己刚设过的值兜住了。

### 一个真实的误伤

用户说「声音低一点」，系统回「已调低到 23 度」—— 而音响一点没变。
因为上一条命令是空调，`last_domain` 是 `aircon`，而"低一点"在空调域里完全合法。
省略了设备名的句子，只能靠上下文补 —— 而上下文本身可能是错的。
修法是把音量类词（声音/音量/太吵）绑死在音频域，不参与 `last_domain` 继承：
**有些词的设备归属是它自己带的，不该让上下文改写。**


## 4.1.20 M13/M14 播放模式与连续对话

### 播放模式

顺序 / 列表循环 / 随机 / 单曲循环，四种，语音可切（"随机播放"、"单曲循环"、"顺序播放"）。

实现上有个选择：随机是**每次随机取一首**，还是**把队列洗一遍再顺着放**。
选了后者（`_rebuild_order`）。前者会重复 —— 十首歌的列表里连着放到同一首的概率高得
用户一定会注意到，而那看起来就像坏了。洗牌保证一轮之内不重复，这才是人说"随机播放"时想要的。

切模式时当前这首**不重来**（`keep_current=True`）：正听着的歌被切模式打断，
是纯粹的损失 —— 用户想改的是"下一首放什么"，不是"这首别放了"。

### 连续对话：窗口该多久，以及沉默什么时候比说话好

一条命令成功之后不用再说唤醒词，蓝灯亮着直接说下一句。上限 5 轮
（没有上限的话，一次误识别就能让麦克风一直开着）。

两条设计是踩出来的：

**只在成功之后开窗。** 失败意味着我们本来就没听懂，这时候开窗是在邀请更多混乱 ——
用户多半会重复一遍或换个说法，而那恰恰是最该走完整唤醒流程、让识别从干净状态重来的时候。

**追问窗口里没听懂，要闭嘴。** 上线第一版的表现是：每条成功的命令后面都跟一句
「这个我还不会」，对着空气。因为窗口一开就录到了回声和尾音，0.7 秒的音频判成"说完了"
发上去，服务端听成「没有。😮」（SenseVoice 的 `🎼`/emoji 标记这时候特别容易冒出来）。
两处一起修：录音短于 900ms 当噪音丢掉；**追问窗口里没听懂就不出声** ——

> 这一轮是我们自己开的窗，并没有在问用户问题。
> 对着屋里随便一点动静开口，比什么都不说糟得多。

注意这条的前提是"没在问问题"。系统**真的问了问题**的时候前提就不成立了，
那时候沉默才是错的 —— 见下一节选歌消歧，它给追问窗口加了个 `asking` 标记。


## 4.1.21 M16 对话层重做：从一个字符串到一个 Context

### 症状：量出来的「不智能」

把 20 句真实说法灌进意图层，结果分成四类：

| 类别 | 例子 | 改造前 |
|---|---|---|
| 指代/省略 | 再来一个 / 不是这首 / 换一个 / 对就是它 | 全部 `none` |
| 多轮回答 | 第二个 / 要黑鸭子的 / 都不要 | 全部 `none` |
| **编造** | 放首周杰伦的歌来听听 | `title='歌来听听'`，去搜一首不存在的歌 |
| 多意图 | 把灯调暗一点然后放点音乐 | 只执行音乐，灯那半句静默丢弃 |

但真正说明问题的是这张表：

```
last_domain=None    | 大一点→light.brightness  关掉→light.off   下一个→none
last_domain=music   | 大一点→tivoli.volume     关掉→music.stop  下一个→music.next
last_domain=aircon  | 大一点→aircon.temp_step  关掉→aircon.off  下一个→none
```

**「大一点」有四个意思，取决于一个记录「上一条命令是什么」的字符串。**
音乐正放着、但你上一句调的是空调，说「大一点」——房间变热。用户一个字都没说错。

### 根因：查的东西不对

`last_domain` 记的是**我们说过什么**，而人省略主语时，心里想的是**现在正在发生什么**。
这两件事经常不是一回事：

- 用手机或实体按钮开的音乐，系统完全不知道 —— 那不是「一条成功命令」
- 刚开机 `last_domain=None`，所有省略句一律归给灯，哪怕灯根本没开

所以换成 `context.py`：先查世界，再查话题。

```
候选域（「大一点」= 灯亮度 / 音量 / 空调温度）
  -> 其中此刻活着的有哪些
  -> 只有一个     -> 就是它
  -> 有好几个     -> 上次说的那个优先
  -> 一个都没活着 -> 才退回默认
```

有一个不对称值得写下来：**「活着」是把候选筛掉，不是加权**。关着的空调不可能是
「大一点」的对象，这是硬约束；「上次聊的是空调」只是偏好。把硬约束和偏好混进
同一个打分函数，是这类消歧最常见的做法，也最容易出「分数刚好压过去了」的怪结果。

改动量比想象的小：`_AMBIGUOUS` 那张表**结构本来就是对的**（规则名 → {域: 意图}），
错的只有选择策略那一行 `table.get(last_domain or "light")`。这是这次最省力的一处 ——
先看清楚已有的数据结构表达的是什么，往往比重写便宜得多。

### 「不知道」不等于「关着」

`WorldState` 每个字段都可以是 `None`。Tivoli 的状态全是影子（§4.1.17），一开机就是 `None`。

`rank()` 分三档、档间不可换算：确定活着 > 不知道 > 确定关着。**`None` 排在
「确定关着」前面**。把不知道当成否，是影子状态最危险的误用方式 ——
一台我们只是没把握的设备，会被当成明确不在候选里。

### 置信度：三种失败在类型上是平等的，只有分数能分开

`Intent.confidence` 不是概率，是「这个结论怎么来的」的分档：

| 分 | 情形 |
|---|---|
| 1.0 | 句子里有明确设备词（「打开台灯」） |
| 0.9 | 泛化词，候选里只有一台确实活着 |
| 0.7 | 泛化词，靠「刚聊过它」定的 |
| 0.5 | 泛化词，不知道也没聊过 |
| 0.4 | 泛化词，确定关着，纯兜底 |

打分函数**必须住在 Context 里**。写过一版放在 `intent.py`，按「它在候选顺序里排第几」
反推 —— 那是错的：排第一也可能只是「一堆不知道里的第一个」。`intent.py` 看不到世界，
就没资格给这个分。

### LLM 挪位置：从「没听懂」到「没把握」

原来只在 `domain=="none"` 时才问模型。但规则层还有一种更坏的失败：**命中了，而且是错的** ——
开机就说「大一点」稳稳落到灯上，屋里可能根本没开灯。这种「自信的错」用户看到的是
设备乱动，比「这个我还不会」难受得多，却从来没机会走到模型那一层。

现在的条件是 `domain=="none" or confidence < 0.6`。

**一个设计时想当然、实现时被推翻的想法**：本来打算让规则和模型**并行**发车，省掉串行等待。
写的时候才发现没有可并行的东西 —— 规则层是微秒级的，命中与否瞬间就知道，
根本不存在「等规则的同时先让模型跑起来」这个窗口。真正省时间的是**不问**（高置信直接执行），
不是早问。

### 喂现场信息给模型，以及一句适得其反的安全提示

`_ground(ctx)` 把世界状态和最近三轮压成几行塞进提示词。效果是决定性的：

```
再来一个   有现场 -> music.next      没现场 -> None
```

这些话的意思根本不在话里面，不给现场，模型结构上就答不出。

但第一版还加了一句「拿不准就答 domain=none —— 猜错一个设备比承认不知道糟得多」。
实测**五句里五句作废**，而且模型明明听懂了：

```
这首太吵了 -> domain=none, reply="太吵了，调低点？"
```

它理解了，然后照着那句话闭嘴。改成「只有和这几台设备都无关时才答 none」之后 6/8。

> 编造不存在的动作有白名单挡着，那才是真风险。
> 让一个答得对的模型闭嘴不是安全，只是失败。

延迟因此从 1.5s 放宽到 2.6s（带现场后实测 1.87~1.96s，1.5s 会砍掉一半正确答案）。
这一秒是划算的：这一层的职责变了，超时的代价从「一句我不会」变成了
「照着没根据的猜测去动真设备」。

### 追问窗口终于接上了兜底路径

`do_utterance()` 里**压根没调过 `arm_followup`** —— 所以「不用再说唤醒词」只对板上那
十几条命令词成立，而点歌这类必须走服务端 ASR 的请求，窗口从来没开过。

修的时候有两个位置讲究：

**开窗放在 `voice_say()` 之后。** 它是阻塞的，所以那一行执行到的时刻正好是喇叭刚停下来
的一刻，窗口从用户能开口时才计时。放前面的话，「一，黑鸭子；二，…要哪个？」这句话
本身就要念五六秒，7 秒的窗口全花在听自己说话上。

**窗口长度由服务端给**（`followup_ms`），因为只有它知道刚才说出去的是什么。
3500ms 在「好的」后面正好，在三个选项的问题后面完全不够。

**`asking` 单独一个字段**，因为「窗口里没听懂」在两种情况下该有相反的反应：
平时窗口是我们自己开的，出声比沉默糟（§4.1.20）；但刚问完「要哪个」时沉默才是错的 ——
用户答了一句，系统一声不吭，他分不清是没听见还是答错了。


## 4.1.22 选歌消歧，以及两个「看起来成功其实在骗人」的 bug

说一首歌，搜得准就直接放，搜不准就把前三个念出来问一句。

门槛定在哪是唯一真正的设计决策：**问多了比猜错还烦**。「播放红豆」每次都要答一遍
「第几个」，用户会直接不用它。所以默认必须是直接放，只有三种「我确实不知道」才开口。

### pop 会饱和在 100 —— §4.1.14 那句结论要更正

原来的判据是「热度拉得开就直接放」。实测站不住：

```
搜「红豆」  pop=100 王菲 / pop=100 方大同 / pop=100 徐泽（要不要买菜）
搜「稻香」  pop=100 Lucky小爱 / 95 Montagem / 95 Lie …  周杰伦的原版不在结果里
```

`pop` 是个粗糙的分桶分数，顶到 100 就不动了。§4.1.14 里「按 pop 排立刻就对了」
是在更窄的样本上得出的，放宽之后不成立。**它只能当平手时的决胜局，当不了主排序。**

结果是同名多版本时基本都会问 —— 而这正好是想要的行为，所以没为它硬造一个排序信号。

### 两个 bug，都属于「比放错更糟」

改造过程中自己写出来的，都是**系统说了一句不实的话**：

**一、歌名「完全相同」输给了「名字里带」。** 搜「周杰伦 稻香」时，一个上传者昵称叫
`周杰伦.`（带个点）的《稻香(治愈版)》因为热度高，盖过了所有歌名正好是「稻香」的结果。
然后系统说「播放周杰伦的《稻香》」。原来的 `_best()` 注释里白纸黑字写着「歌名先于歌手」，
我重写时把这条丢了。

**二、歌手名「只是包含」被当成了命中。** `周杰伦.` 含 `周杰伦`。展示用的 `_is_artist`
故意放得宽（合唱也算），但**这一步的后果是「不问就放」，门槛必须更高** ——
主唱名字完全相等才算。网易云上冒用原唱名字的上传者非常多。

修完之后「播放周杰伦的稻香」的回答是：**「网易云上没有周杰伦的《稻香》。一，Lucky小爱，
二，Lie，三，Montagem。要哪个？」** —— 他的曲库确实整个不在这个平台上。

### 「的」不一定是分界符

「月亮代表我的心」被规则劈成 歌手=`月亮代表我` / 歌名=`心`，于是系统说
「网易云上没有月亮代表我的《心》」。

没去给正则打补丁（「的」前面几个字算歌手，这种规则永远有反例），而是**让曲库裁决**：
整句话如果本身就是一首歌的名字，那这个「的」就不是分界符。索引比正则更懂什么是歌名。
代价是多一次搜索，且只在规则真的劈过时才花。

### 离线测得对，走完整链路却不对

`_pick_or_ask` 单测全过，端到端一跑却直接放了综艺版 —— 因为
**规则层只在「某某的某某」形态下才填 `title` 槽**，而人多半直接说「播放花儿与少年」，
那种句子只有 `query`，走的是末尾「搜一下放第一个」的老路径，消歧整个绕过去了。

> 单测证明的是「这个函数对」，不是「这条链路会走到这个函数」。

### 选项念不完 = 没问

搜「花儿与少年」回来全是综艺主题曲，一首歌挂着七到九个演员。三个选项照实念要二十多秒，
用户早忘了第一个是什么。所以歌手超过两个就压成「华晨宇等7人」，回话里也用同一套截断。

### 最重要的一条：不许吞掉用户的话

一个悬着的问题如果会**吞掉**下一句，用户在问题之后说「打开台灯」就会石沉大海，
而他根本不知道系统还在等一个答案。所以 `_parse_choice()` 认不出来时还回 `None`，
调用方继续走正常流程，同时**把问题撤掉** —— 用户已经用行动表示不打算答了。

实测：

```
你: 播放月亮代表我的心
机: 《月亮代表我的心》有几个版本。一，王小帅、周明明，二，邓丽君，三，张国荣。要哪个？
你: 打开台灯
机: 灯开了
```


## 4.2 环境搭建踩坑

- Homebrew 的 `python@3.14` 的 `ensurepip` 是坏的，而 IDF 的 `detect_python.sh` 只找 `python3`，
  会挑中它然后建 venv 失败。解法：`~/.espressif/pyshim/python3 -> python3.13`，并在 `firmware/env.sh`
  里把 shim 放在 PATH 最前面。
- `~/.cache/huggingface/token` 里存着一个失效的旧 token，`huggingface_hub` 会带着它去请求
  **公开**仓库然后被 401 拒掉，报错信息还是误导性的 "Repository Not Found"。
  解法：`HF_TOKEN_PATH=/nonexistent/hf_token`（已写进 `server/.env.example`），不用动原文件。
- 环境里有 `all_proxy=socks5://...`，httpx 走 SOCKS 需要额外装 `socksio`，否则 ImportError。
- esp32s31 在 v6.1 里是 preview，**所有 `idf.py` 命令都要带 `--preview`**：
  `idf.py --preview set-target esp32s31` / `idf.py --preview build`。

## 5. 已知坑

- 同目录的 `esphome/config/audio.yaml` 是**另一块板**（ESP32-S3-Korvo-1）的配置，跟本项目无关。
- `xiaomi_home` 集成的 OAuth 回调地址**硬编码**为 `http://homeassistant.local:8123`
  （`miot/const.py`，且 `config_flow.py` 用 `vol.In([...])` 做成了单选项下拉框，UI 改不了）。
  HAOS 会用 Avahi 广播这个 mDNS 名字，**纯 Docker 装法不会**，于是浏览器 NXDOMAIN。
  解法：`/etc/hosts` 加一行 `127.0.0.1 homeassistant.local`。
- **喇叭没出声（M4 唯一没通的一段）。** 排查到的事实：`esp_codec_dev_write()` 返回 OK，
  2.85s 的音频恰好耗时 2.85s（说明 I2S TX 在按 16kHz 实时出数），PA 使能脚 GPIO57
  实测是**高**的（注意 `gpio_get_level` 在 `GPIO_MODE_OUTPUT` 下恒读 0，要先切
  `INPUT_OUTPUT` 才读得到真实电平，我先被这个骗过一次），强制再拉高没有任何变化，
  ES8311 寄存器全部符合驱动预期（0x31 未静音、0x32 音量 0xA8、0x12 DAC 已使能、
  0x44=0x58 是驱动有意写的内部参考）。用 Mac 麦克风录板子放 1kHz 正弦，
  FFT 在 1kHz 频段上**毫无痕迹**。软件侧没有嫌疑了 ——
  诊断代码留在 `audio_hw_diag()`，在 `main.c` 里注释掉了，排查时打开即可。
  （README 里 M2 那句"喇叭能回放"当时多半也只验到了"write 返回 OK"。）
  **后续（原理图查证）：板子出厂不带喇叭，Speaker Output Port 只是个接口** ——
  背面 J9（`CON02_CC_S_2G`，1.25mm 2pin），由 U9 NS4150B 的 `PA_OUTL±`
  经 L3/L5 两颗 0Ω 磁珠过来，测试点 TP4/TP5 就在这两根线上；官方指南写明
  "最大可驱动 4Ω 3W 喇叭"。BTL 差分输出，**两根都在摆，任何一根都不能接地**。
  没接喇叭期间用 `CONFIG_S31_HAS_SPEAKER=n`（默认）把取 TTS 那段整个跳过，
  省掉开机的 3.5s 和每次兜底的约 1.5s；接上喇叭后打开这一项即可恢复，代码不动。
  没有声音的时候，兜底路径上"听懂了但做不了"改由**黄灯闪两下**表示 ——
  否则灯不变，用户无法区分"没听见"和"听见了但不会做"。
  **数字段现在有正证了**：DAC 回环自检测到 1kHz 幅度 8654/12000（见 4.1.7），
  所以缺的确实只是喇叭本身。模拟输出和 NS4150B 仍然未验。
- **真人语音只测过一次**（用户本人对着板子说「你好小智」+「打开台灯」，成功）。
  其余全部结果都是 TTS 合成语音、安静房间、约 2 米、笔记本扬声器。
- **声学回归会被屋里的人声污染**。实测撞过一次：跑回归时旁边说了句「关闭台灯」，
  被脚本算成了那次播放的结果，判成"误识别"，差点让我去 A/B 一个根本没坏的改动。
  `mn_regress.sh` 现在会在一个窗口里听到多条命令词时告警，但**跑回归时屋里要安静**。
- **嘈杂环境基本叫不醒**：SNR 10dB 还是 6/6，5dB 掉到 1/6，0dB 全灭（4.1.11）。
  这是目前最硬的限制。要改善只能上降噪（`se_init` + nsnet2），但得先有嘈杂环境的回归。
- 唤醒词的其余几项都测过了：误触发（静默 30 分钟 0 次；干扰语料下日常句子 0/36、
  近音词 8/21、误动灯 0）、灵敏度（−12dB 仍 5/6）。**但真实远场（带混响）仍然没测** ——
  衰减代理是性能上界，抱着板子走才算数。
- AEC 是关的（单麦、没把喇叭信号接回 AFE 当参考通道）。现在靠 `sr_set_muted()`
  在放 TTS 期间给麦克风喂静音来回避 —— 代价是**放回话时听不见你说话**（不能打断）。
  想支持打断就必须补 AEC。**参考通道现在已经现成了** —— I2S 右声道就是 DAC 回环
  （见 4.1.7），剩下的是把 AFE 从 "M" 改成 "MR"、`aec_init=true`，再把两路交织着喂进去。
  没做：没喇叭就没有真实回声，做了也验不了。
- ~~`nsnet2` 打进了 flash 但没进流水线~~ 已换回 WebRTC，省 330KB，见 4.1.10。
- ~~命令词表只在开机时拉一次~~ 已支持热更新（60 秒轮询版本号），见 4.1.8。
- ~~服务端没有鉴权~~ 已加共享 Bearer 令牌，见 4.1.9。注意它**不是** TLS：
  令牌在局域网里是明文传的，威胁模型只到"同网段的其他人别乱按我的灯"。
- **控灯的 ~0.4s 是灯泡自己的**（miIO UDP 往返中位 374ms，见 4.1.6），
  快路径 93% 的时间花在这儿，软件侧没得优化了。
- HA 的 Nabu Casa 云订阅返回 401，`stt.home_assistant_cloud` / `tts.home_assistant_cloud` 两条 pipeline 都是废的，必须换本地引擎。
- `configuration.yaml` 里的 `yahoofinance` 平台已不存在（HACS 没装），每次启动报错，不影响功能。
