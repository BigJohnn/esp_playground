# sanoTTS 对本项目的适用性评估

评估日期：2026-09-16。范围：`s31_voice` 的中文回话合成，以及同仓库 S3-Korvo-1 的试验价值。

本次核查了项目代码、已有测试记录和 sanoTTS 上游文档，没有安装或实测 sanoTTS，也没有重新运行 Kokoro 横评。下文区分已有记录、上游自测和后续建议；上游链接指向可变的主分支，正式试验时应固定提交与模型版本。

## 结论

**当前保留 Kokoro，不直接替换。优先缓存常用回话；sanoTTS 作为轻量候选后端，经过中文对照测试后再决定是否切换。**

sanoTTS 的小模型和板端推理值得参考，但“337KB”“支持中文”“ESP32 实时”属于不同模型与运行配置，不能合并为本项目可直接获得的能力。当前系统已经在 Mac 本机合成语音，无需云端 TTS；替换引擎本身不会消除对 Mac 的依赖。

## 文章中的指标应如何理解

| 项目 | 核查结果 | 对本项目的影响 |
|---|---|---|
| 337KB 权重 | 对应英文 heart-nano，约 29.4 万参数 | 不能按此估算中文模型大小，更不等于完整固件大小或运行内存 |
| 中文小雅 | `chinese-xiaoya` 约 155 万参数，使用拼音前端 | 需要单独验证中文权重、前端、内存和速度 |
| RTF 0.383 | `BOARDS.md` 对应英文 `en_us_e12nano`、ESP32-S3、Xtensa LX7 PIE SIMD；同表标量 C 为 1.5825 | 不是中文小雅的成绩，也不是 337KB heart-nano 那套权重的直接实测 |
| 本项目芯片 | ESP32-S31，RISC-V，ESP-IDF 工程 | 不能直接复用 S3 的 Xtensa 汇编优化；已查资料没有提供本项目配置的实时依据 |
| amy 的自然度分数 | 是英文声音的上游自动评测 | 不能据此推断小雅的中文回话质量，更不能直接替代本项目测试 |

来源：[上游 README](https://github.com/Ampixa/sanoTTS)、[BOARDS.md](https://github.com/Ampixa/sanoTTS/blob/master/BOARDS.md)、[浏览器声音配置](https://github.com/Ampixa/sanoTTS/blob/master/web/index.html)。RTF 是计算耗时与生成音频时长之比，小于 1 表示快于播放速度，不等于首音延迟。

中文评测也需区分口径：浏览器页面列出 CER 0.024，其代码注释引用 FLORES 的 0.199；核查时 README 另列 24 句留出集 CER 0.201。这些不能混作同一测试结果，也不能和本项目的 15 条回话匹配率直接比较。上游明确说明非英语声音尚未做听音测试。

Python 接入能力需要按实际版本验证：上游 README 仍将中文列为浏览器支持，而主分支 Python 前端已经出现拼音类型支持，文档与实现存在更新不同步。正式试验应核实安装包、中文模型包和前端能否完整配套，不能把浏览器演示成功等同于 `pip install` 后即可直接替换服务端。参考 [Python 前端源码](https://github.com/Ampixa/sanoTTS/blob/master/pypkg/sanotts/frontend.py)。

## 当前实现为什么值得保留

- [服务端配置](../server/config.py) 默认使用 `hexgrad/Kokoro-82M-v1.1-zh`、本地权重和 `zm_011` 音色，已经修正早期使用 v1.0 权重导致的中文问题。
- [已有横评记录](../README.md#415-tts跑错权重花了大半天)中，`zm_011` 为 12/15 整句匹配、59/66 逐字匹配；当时将剩余差异归为同音字和数字规整。这是小规模场景测试记录，不是通用中文质量保证。
- [pinyin_fix.py](../server/pinyin_fix.py) 修复了“调到、调亮、调暗”等场景词。更换中文前端后，这些修复不会自动迁移，必须重新验证。
- [tts.py](../server/tts.py) 已将模型输出统一为 16kHz 单声道，并提供 float32 音频和 16-bit LE PCM 接口。后续候选引擎可沿用这些边界。
- [app.py](../server/app.py) 的 `/tts` 先完成整句合成，再返回音频；板子边接收边播放不等于模型已经流式输出。[固件快路径](../firmware/main/main.c)的普通命令成功后不念回话，因此替换 TTS 不会普遍缩短控灯延迟。

## 建议的改进顺序

### 1. 缓存常用回话

当前 `/tts` 每次调用都会进入合成，适合先缓存“我没听清”“这个我还不会”等重复文本。缓存键应包含文本、引擎/模型版本、音色、语速和输出采样率；设置容量上限，防止动态回话无限增长。对缓存命中的短句，可省去重复合成等待并保留现有音质。

### 2. 用预生成音频提供有限的板端离线提示

若目标是 Mac 不可用时仍能提示“服务暂时不可用”，可先将少量固定音频放入固件或文件系统。16kHz、单声道、16-bit PCM 每秒约 32KB，十条平均两秒的提示语约 640KB，实施前需检查实际分区余量。

这种方式仅解决固定提示音的播放，不提供任意文本合成，也不会让原本依赖服务端的识别、意图和设备执行自动离线化。

### 3. 在服务端增加 sanoTTS 实验后端

保留 Kokoro 为默认值，让候选引擎遵循现有 `synth()`、`synth_pcm()`、`synth_pcm_async()` 接口，保持 16kHz 输出和板端协议不变。固定版本、预先准备模型，在模型初始化失败时明确报错或回退，并验证资源准备完毕后的离线合成。

先在 Mac 上比较中文正确性和资源收益，再决定是否投入板端移植。只有候选引擎在本项目实际回话上通过验证，且解决了明确的内存、部署或延迟问题，才考虑修改默认配置。

### 4. 把板端移植作为独立试验

同仓库的 [S3-Korvo-1 配置](../../esphome/config/audio.yaml)更接近 sanoTTS 的 S3 优化路径，可以作为试验平台；它与 S31 主项目是两块不同的板。仍需验证中文模型、前端、I2S 输出，以及与 AFE、WakeNet、MultiNet、Wi-Fi 同时运行时的内存和调度开销，不能用纯推理 benchmark 代替整机验证。

## 替换前的验证条件

- 使用 [voice_bench.py](../tools/voice_bench.py) 的 15 条实际回话，并补充数字、百分比、歌手名、多音字和较长的追问文本。
- 在相同输出采样率下比较 Kokoro 与小雅；结合人工听音和 STT 回转结果，单独记录发音错误、识别错误和数字格式差异。
- 分开测量冷启动、稳态纯合成耗时、首音延迟、RTF、峰值内存与模型文件大小。现有脚本的“合成”计时包含 STT 耗时，不能直接用作引擎速度指标。
- 现有逐字计分使用 `zip()` 按位置比较，并非标准 CER；引擎横评应增加基于编辑距离的 CER，避免插入或删除一个字导致后续全部错位。
- 在真实喇叭与麦克风链路上复核，并在更换默认引擎后重跑依赖合成语音的声学回归，防止测试输入变化污染结论。

以上均为待实施建议。本次仅记录选型结论，没有更换引擎、增加缓存或执行板端部署。
